## Pending — 2026-05-30 (Wave 2 — opt-in RPC socket token)

Source: `doc/full_app_review_2026-05.md` §6.1. Tracking: `doc/tracking_wave2_socket_token.md`.

- **Optional RPC socket token (default OFF)** — new setting **Settings → Network → "Require RPC socket token"**. When enabled, the `ht` socket requires a per-boot token (`socket.token`, 0600, beside the socket) for state-mutating commands; read-only diagnostics stay open. The bundled `ht` and the pi/Claude bridges read+present it automatically; older external `ht` installs lose mutating commands until updated. New env override `HT_RPC_TOKEN_PATH`.
  - Document the setting + threat model (defense-in-depth vs opportunistic same-user processes, not a hard boundary) on a security/config page (en + fr); add a changelog entry. Note `HT_RPC_TOKEN_PATH` in the `ht` env-var reference.
  - **Deferred (noted):** OS-keystore encryption of cookies/secrets at rest — Electrobun has no persistent Keychain API; planned as a separate change.

## Pending — 2026-05-30 (Wave 1 security hardening)

Source: `doc/full_app_review_2026-05.md` §1.1 Wave 1. Tracking: `doc/tracking_wave1_security_hardening.md`.

- **Web-mirror auth token / bind apply live (W1-1)** — changing the auth token or bind address in Settings now takes effect on the running mirror without a restart (token in place; bind via re-listen). Token rotation also clears the brute-force cooldown. Changelog line; no API change.
- **`ht browser navigate` no longer accepts `file://` (W1-4)** — **user-visible CLI change.** A `file://` URL is now rejected (it allowed local-file read via a pane over the socket). `http(s)://` (incl. localhost dev servers), `about:`, `data:`, `chrome-extension://` still work. Note in `cli/` browser docs (en + fr) + changelog.
- **`browser.addscript`/`addstyle` now enforce the 256 KiB script/CSS cap (W1-4)** — same cap as `browser.eval`; only affects pathologically large payloads. Changelog only.
- **Internal hardening (no doc change beyond changelog):** brute-force throttle keyed on the real peer IP; secrets-at-rest write window closed (atomic-write tmp created `0600` + fsync); logger redacts telegram/auth tokens before the on-disk tee.

## Pending — 2026-05-30 (Wave 0 ship-stopper security fixes)

Source: `doc/full_app_review_2026-05.md` §1.1 Wave 0. Tracking: `doc/tracking_ship_stoppers.md`. These are **security-behavior changes** that should be called out in the changelog + the relevant feature/security docs (en + fr).

- **Web mirror now honours bind + auth token on auto-start (C1)** — previously the auto-start and port-change paths bound `0.0.0.0` with no auth regardless of `webMirrorBind` / `webMirrorAuthToken`; only the manual Settings toggle respected them. All construction now goes through one `createWebServer()` factory and the `WebServer` constructor's bind/authToken params are required. **User-visible:** a configured loopback bind / auth token now actually takes effect when the mirror auto-starts at launch.
  - Update `website-doc/src/content/docs/features/web-mirror.md` + any security/network page (en + fr): the auth token + bind setting now apply to auto-start, not just the manual toggle. Add a changelog entry.
- **Telegram allow-list is empty by default and fails closed (C4 / H0a)** — `telegramAllowedUserIds` default changed from a hardcoded id to `""`, and an empty allow-list now **rejects all** inbound messages and button taps (was: accept-everyone). **User-visible:** users must enter their own numeric Telegram id in Settings → Telegram before the bot will act on their messages; a one-time warning is logged while the list is empty.
  - Update `website-doc` Telegram setup docs (en + fr): document that the allow-list must be populated (empty = no access), and the fail-closed behavior. Add a changelog entry.
- **`auditsGitUserNameExpected` defaults to null (H0g)** — the git-username audit is opt-out by default (was hardcoded to a specific username). No doc change beyond a changelog line unless the audit is documented.
- **Inline sideband panel HTML/SVG is now sandboxed in the web mirror (C2)** — inline `meta.data` html/svg payloads render in the same sandboxed iframe (CSP `script-src 'none'`) as binary frames, closing a LAN-XSS hole. No user-facing API change; mention in changelog under security.
- **CI/release hardening (H0b / H0c)** — release workflow now runs typecheck + tests before uploading binaries; CI re-runs the functional (non-pixel) web-mirror e2e specs. Dev-process only; mention in `development/` docs if release-process page is touched.

## Pending — 2026-05-19

- **HTTP web mirror terminal sizing fix** — three coupled issues fixed: (1) `.pane .xterm` had `padding: 6px 8px 8px;` in `src/web-client/client.css` while native (`.surface-terminal .xterm`) has none, so the shared fit math (`src/shared/xterm-fit.ts`) computed ~1-2 fewer cols on the web side than what native had already advertised to the PTY — every `clear` surfaced zsh's `%` PROMPT_SP cookie and long lines wrapped one col short. Removed the padding so web/native cell math match. (2) The server already plumbs `surfaceResizeRequest` (`src/bun/web/server.ts:1204`) but `ws.onSurfaceResizeRequest` was never assigned in `setupWebServerCallbacks` (`src/bun/index.ts`), so every web-mirror resize proposal was silently dropped. Now wired to `sessions.resize` + `ws.sendResize` so the web mirror can actually drive PTY size (last-write-wins with native's `viewport.resize`). (3) Browser-window resize did not refit panes in `nativeViewport` mirror mode because `applyLayout` writes rects in native pixels and only the container's CSS transform changes — the per-pane `ResizeObserver` never fired. Extracted the propose-if-changed helper out of the RO callback into a per-surface `proposeResize` and call it (plus `fitTerminal`) for every pane from the window-resize debounce in `src/web-client/main.ts`. (4) Added a `+0.5` pixel epsilon to the `cols/rows = Math.floor((w − padX) / cell.width)` math in `src/shared/xterm-fit.ts` and `src/views/terminal/surface-manager.ts` so sub-pixel DOM measurements (e.g. 1199.6 vs 1200) no longer shave a whole column.
  - Add a changelog note (en + fr) when updating `website-doc`. Tag: web-mirror parity.

- **Native webview now loads design tokens (v0.3.158)** — ROOT CAUSE for the v0.3.155 → v0.3.157 series of failed ask/plan modal opacity fixes. `src/shared/web-theme-tokens.css` is the canonical token block (333 `--ht-*` tokens referenced by `index.css`), but it was only being served to the web mirror via `vendor/web-client/tokens.css`. The native webview's `index.html` only loaded `xterm.css` + `index.css`, so every `var(--ht-*)` reference in the native webview resolved to "invalid at computed-value time" — i.e., for `background` properties, fell back to `transparent`. Most chrome survived because its last cascade rule used a locally-defined token like `--t3-card` or `--tau-panel-hi`, but `.ask-user-sheet` had only ONE background rule (`var(--ht-ask-sheet-bg)`), so it has been completely transparent in the native app since the Cluster H token migration. The earlier v0.3.156 / v0.3.157 fixes only ever worked in the web mirror — they were invisible in the native app, which is what the user was running. Fix: `src/views/terminal/index.html` now `<link>`s `theme-tokens.css` BEFORE `index.css`, and `electrobun.config.ts` copies `src/shared/web-theme-tokens.css` → `views/terminal/theme-tokens.css` so the same canonical token block ships to both surfaces. Side effect: any other element whose last cascade rule used a `--ht-*` token (and was therefore silently transparent in the native app) will now render with its intended color. Specifically the `.prompt-overlay` scrim — which used `var(--ht-ask-scrim-bg)` as its last rule — was previously transparent and now correctly shows the heavy 0.86 black scrim.
  - Add a changelog note (en + fr) when updating `website-doc`. The note should call out the root cause (tokens.css never loaded by the native webview) since it likely explains other "subtle chrome looks off in the native app vs the web mirror" bug reports the user may have dismissed.
